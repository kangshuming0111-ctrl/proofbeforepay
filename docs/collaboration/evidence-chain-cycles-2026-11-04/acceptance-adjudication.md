# Supplemental acceptance chain: independent adjudication

Date: 2026-11-04. Scope: three existing supplemental evidence families, buyer selection, immutable acceptance objects, stale-view and concurrency protection. Code was edited locally; this child task did not commit, deploy, send a real payment, or submit Devpost material.

## Implemented boundary

- Server revalidates source-visibility, deployment-source and time-policy full records. Public object hashes cover the validated public projection, with participant actor identifiers withheld. Time HTTP bodies retain only finite protocol fields; arbitrary native response fields and customer data do not enter the public object.
- The complete current catalog, latest public artifact manifest and current follow-up heads participate in the catalog digest. Every report must be included or explicitly excluded. Every included mismatch/unknown finding requires its exact checkbox acknowledgment and a buyer reason. Unexecuted policies cannot be included; running reports must finish or close.
- Open/proposed follow-ups require separate buyer reasons and exact current task versions. A task resolution does not rewrite an original finding or automatically accept delivery.
- New acceptance snapshots freeze the complete reviewed catalog rows/context and exact object references. Their full public objects, including excluded planned records, are conditionally inserted into a separate immutable archive in the same D1 batch as the guarded quote update. Quotas reject additional objects; existing objects are not pruned. Old accepted snapshots and capture consent are not reconstructed or rebound.
- Three report-table counts and exact identity/version sets, the latest manifest id/digest and follow-up state are checked in the acceptance UPDATE itself. Independent report changes cannot slip between a pre-read and acceptance. SQL JSON sets keep the full supported capacities below D1's 100 bound-parameter ceiling; the tested combined quote guard uses 41 parameters even with the extra task guard.
- Overview shows separate evidence layers. The compact bilingual selection panel uses the parent authenticated request helper. Project/delivery/role/catalog/stage/payment context, a generation fence and mounted state prevent old asynchronous replies from replacing a newly selected view. The server mutation itself is not replayed or falsely represented as cancelled.

## Concrete issues found independently and fixed

1. **Manifest coverage was not implied by equal static-delivery digest.** A v1 or older v2 byte report could otherwise remain visually supported after a new build manifest. The catalog now adds an `artifact_manifest_changed` unknown. Missing/unavailable v2 script references remain individual unknowns; v1 JavaScript coverage and v2 complete-dependency-graph limits stay explicit unknowns requiring buyer acknowledgment or exclusion.
2. **Arbitrary time-adapter response extras could contain private data.** The public time-body projection now keeps only semantically relevant protocol fields, removes customer/email and arbitrary extras, normalizes irrelevant invalid values, then reruns the original native validator. A genuine independently executed SQLite run still supports all 12 original finite cases after projection.
3. **Maximum-capacity CAS could exceed the provider's parameter ceiling.** Expanded scalar id/version predicates were replaced by bounded JSON arrays and `json_each` membership checks, preserving counts and exact identities. Cloudflare's current primary documentation states a maximum of 100 bound parameters per query: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
4. **Canonical public hashes conflicted with object-key-order-sensitive native comparisons.** Time-policy comparisons for cases, expected requests, policies and results now compare canonical object structure while preserving array order. Source-visibility summaries validate strict known keys and rederived individual counts. Reordering JSON member keys preserves a public reference; changing counts or array order does not become an accepted observation.
5. **A stale asynchronous panel response could target a newer project view.** The panel now fences every success, error and busy callback by its original context and generation, and blocks repeated immediate submits with a synchronous ref.
