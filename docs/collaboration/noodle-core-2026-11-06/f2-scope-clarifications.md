# F2 — Bilateral scope clarification for the fixed noodle-shop flow

## Observable scope

A participant selects a delivered page or an explicitly identified HTML form for one unchanged original requirement. Proposing confirms neither party. Buyer and seller must each explicitly confirm the same immutable proposal. An agreed scope selects the material to recheck; it does not establish correct labels, price, visibility, submission, storage, acceptance or payment. One-owner role play is labelled separately from authenticated participant actions.

The original requirement, prior decisions and prior AI report remain readable. A new proposal supersedes the older decision for that criterion immediately, even before it has both confirmations. Scope mutation archives the exact current assessment (at most four retained reports, no eviction) and clears the current cache, allowing a fresh assessment. New uploads do not inherit AI reports or assessment history. Bilateral scope can carry to a later delivery only while the original criterion/source is unchanged and its page/form resolves uniquely in that actual version. A pending old-version proposal cannot be confirmed after replacement.

## Before and award reference

Before this slice the product already had ordinary change requests, immutable delivery history, a conservative scope-question draft, risk annotations and independent source checking. It lacked a durable bilateral page/form decision and an exact saved mapping context for later rechecks. This is the gap being addressed; those existing features are not claimed as newly invented.

Primary reference: [AI Builders Challenge with IBM Bob 2026 winners](https://www.bemyapp.com/insights/ai-builders-challenge-with-ibm-bob-2026-winners.html), inspected in the November 6 source review. ## Plan critique and independent decision

The bounded read-only plan packet and valid review are retained as `outputs/noodle-core-2026-11-06/f2-plan-deepseek.json`. Independent adjudication is `f2-plan-adjudication.json`. Accepted integration hazards: all closed export allowlists and reconstructed quotes must include scope; exact report prefixes must be replayed; scope and report-history bytes must participate in the existing budget; accepted/pending operations need explicit mutation guards; list projections must omit heavy records.

The suggestion to delete the project scope log when a new version has an unavailable target was rejected. Deletion would destroy the original decision. The implementation retains the log and reports the current mapping unavailable instead. A dedicated scope guard is used rather than widening the existing generic action union. The scope log itself is the append-only audit source; no unrelated event type was invented.

## Code and authority

- `lib/scope-clarifications.ts`: deep domain boundary, strict proposal/confirmation input, original source and finite target validation, current authority, historical prefix reconstruction, bounded retention.
- `app/api/proofs/[id]/scope-clarifications/route.ts`: existing authenticated membership role, existing D1 compare-and-swap, no mutation retry; GET/POST return `{quote, role, scopeContext, candidates}`.
- `lib/contracts.ts`: optional scope/history/report-context types, legacy absence preserved. F1 owns its separate sourceFinding/modelJudgment item fields.
- `lib/evidence-export.ts`: project log and declared mode, retained assessments and exact prefix replay. F1 independently recomputes its source finding against that report's reconstructed scope. The envelope remains unsigned and does not prove participant identity.
- `lib/evidence-budget.ts`: aggregate 12-proposal/64-KiB scope cap and four-report retained assessment cap; actual UTF-8 bytes contribute to the existing 256-KiB shared history and hydrated delivery limits. No record is evicted.
- `lib/proof-workflow.ts` and `lib/proof-store.ts`: exact old-version scope snapshot, new-version AI history reset, heavy-list projections.

All mutation authority comes from the server's actual `record.role`. Owner roleplay requires the existing explicit creation markers; two actual accounts use membership-derived buyer/seller roles. Request JSON cannot assign role, mode, timestamps, proposal digest, confirmation history or a report's scope stamp. Distinct concurrent writes rely on the existing version CAS and require manual refresh after a conflict.

They include malformed input, stale delivery/source/latest proposal, one-sided confirmation, two explicit role actions, superseding proposal, revision carry and missing target, pending old-basis rejection, immutable old report/prefix replay, no eviction, UTF-8/shared budget, replacement history, and offline metadata tampering. These are controlled local tests, not real participant or provider execution.

`f2-post-deepseek.json` is the first valid focused postreview. Its only finding was a P3 claim that hidden/inert fieldset ancestors were not excluded, and that disabled inputs should prevent a form scope. Independent pure executions retained in `f2-post-counterexample.json` show hidden/inert ancestors already excluded. A disabled input remains owned by its source form; the mapping does not assert interactivity. The suggestion was rejected to preserve that distinction.

Independent self-review then reproduced a real bounded omission: the original explicit native phrase `The form source in contact.html ...` was not recognized by the older generic file hint and could receive a proposal for another file. The finite native directive parser now rejects that conflict and a regression checks both rejection and the matching-file positive case. No basename or model-prose mapping was added. A separate final narrow postreview is retained as `f2-native-fix-post-deepseek.json`; final adjudication and source freeze are recorded alongside it.

Parent-owned isolated D1/API, actual two-account and live/browser verification are separate receipts. There is no claim here that the fixed source form saves records, that a disabled input works, that humans found the onboarding easy, or that the product is stronger than a published award winner.

Final narrow review was valid and reported no P1/P2. The suggestion to require a form already containing every requested label was rejected: it would prevent choosing a defective form for correction and confuse scope with compliance. An unsupported native-looking single-label expression remains a qualified boundary (see `f2-native-unsupported-boundary.json` and `f2-final-adjudication.json`); it is not used by the fixed noodle example. Root explicitly declined a blanket ban on clarification of unsupported wording. No broad grammar, basename inference or acceptance rule was added. Final observed source hashes are in `f2-owned-source-freeze.json`.

The exact unsupported single-label boundary was subsequently closed with the root-approved `explicitNativeLabelFile` restriction: one safe filename in the anchored own-source prefix, outside balanced quoted data and recognized global/conditional contexts. Unsupported label semantics remain unsupported and the same file remains available for bilateral clarification. No blanket native-family ban was added. `f2-prefix-post-deepseek.json` is valid with zero findings; final related tests are 73/73 (14 new scope tests), and `f2-prefix-type.log` records a zero-error typecheck. This supersedes the earlier qualified single-label boundary while preserving that original before receipt.

The already explicit v4 publication migration remains separately counted and is never labelled unchanged publication.
