# Diagnosis cycle — result and remaining product gaps

Date: 4 November 2026, Australia/Melbourne. This is a read-only scope and gap record at the implementation review checkpoint. Later hosted observations belong to the release ledger and should not be inferred from constructed local UI fixtures.

## This cycle's completed implementation scope

This cycle implements **priority1: expose and explain the existing concurrent-state evidence, with a precise repair/retest path**, plus optional report-bound AI explanation. It does not complete the entire preceding multi-priority roadmap.

The current source adds:

1. A pure diagnostic projection over existing immutable model reports. It presents expected/actual business differences, original-booking party impact, canonical observation references and explicit retest guidance while preserving the existing oracle verdict.
2. A primary overview spotlight for pending, unverified, invalid, violated, inconclusive and compatible model evidence. The spotlight computes a digest from actual current files before presenting a result and labels original accepted evidence separately from supplements.
3. A compact detailed diagnosis and a bounded editable change-request draft tied to the exact current model report. Creating a draft does not submit feedback or accept work.
4. A two-version comparison that requires distinct chronological deliveries, the same project, model/plan digests and equivalent generated inputs. Results are described as still observed, not reproduced in this run, or needing review. Non-reproduction is not a proof that every possible interleaving is repaired.
5. Optional AI explanation over the allowlisted deterministic facts. It binds to report, delivery/file/plan/spec and diagnosis revision/finding inventory; it cannot change severity, verdict, acceptance or payment. The server checks current context before and after the provider call, and saved advice is revalidated before display/export.

The existing `release-vs-transfer-v1` family, original twenty-step journey and31-step HTTP protocol were not expanded or redefined by this presentation/diagnosis work. More engineering tests do not mean more distinct defect families.

## 1. External seller onboarding remains manual

The seller manifest guide still performs local validation/download and asks for operator approval out of band. It does not provide a persisted registration application, operator queue, rejection reason or seller-visible approval lifecycle. Actual targets still come from the operator-owned registry and bind the exact project, upload digest and approval window.

Next useful slice: saved, bounded integration requests with visible requested/approved/rejected/expired states, a complete adapter for one real supported stack, and a conformance preflight. Existing approval and target restrictions must remain; submitting a request must not grant arbitrary URL access or approve its own target.

An independent developer successfully connecting a separately authored implementation would be stronger evidence than another developer-operated variation of the existing fixture. This cycle does not claim that independent onboarding occurred.

## 2. A second state-conflict family and real conditional rules remain

The new diagnostic projection still studies the same cancellation-versus-transfer family. Changing a seed changes party size and three-slot permutation, not the business conflict being tested. The twenty-step lifecycle recipe remains fixed6/8. The separate31-step HTTP protocol already has configurable bounds and concurrent-create checks; it must not be described as wholly unparameterized or lacking concurrency.

Next useful slice: introduce a separately versioned lifecycle recipe or second independent oracle for a concrete conflict, such as two transfers competing for remaining capacity or cancellation and transfer of the same booking. Add one explicit conditional rule, such as a cancellation cutoff or opening-hours/timezone rule, with buyer clarification and bounded executable semantics. Do not rewrite old recipe digests or replace uncertainty with arbitrary AI-generated executable scripts.

## 3. Continuous same-version retest capacity remains constrained

Retained evidence still shares the existing256KiB history budget and fixed per-run reservations. Refusing a run before I/O and retaining old evidence are correct protections. However, an evidence-heavy delivery can still require a new version before another run, even if the user intended to retest the same saved files.

Next useful slice: display current retained usage and the next run's reserved requirement before consent. Then separate large immutable reports from quote metadata using bounded report storage and stable digest/references. Preserve quotas, admission checks and frozen acceptance references; do not silently delete old evidence or simply increase a monolithic JSON limit.

No report-storage migration or new capacity UI is included in this cycle.

## 4. Independent generalization and first-use evidence remain limited

The existing evaluation includes real model calls, complete supported source inputs, licensed static templates, controlled native SQL counterexamples and developer-operated buyer/seller and Sandbox flows. These are valuable and must retain their real successes and limits.

They do not establish accuracy on unknown real projects or independent novice usability. The recorded first-use table still does not constitute completed external participant testing. Small followup sets used while modifying prompts are not held-out benchmarks, and precise citation offsets alone do not prove the explanation follows from the quotation.

Next useful slice: freeze unseen requirement/delivery pairs before remediation, retain complete responses, separately measure missed defects, false alarms, reasonable unknowns, explanation mistakes and citation mistakes, and obtain independent human annotation where available. Independently authored backends add implementation variety but do not substitute for genuine human usability observations.

## 5. Actual deployment and execution provenance remain separate

Exact upload/registration binding and consistent seller readbacks do not prove that the remote deployment was built from the submitted source or that seller-controlled interfaces report an honest database. The cooperative browser bridge remains a client observation, not browser attestation. Offline export verifies self-consistency and original references, not authenticity, payment or an audit of the whole website.

Next useful slice: one authorized isolated staging-browser witness with retained DOM/screenshot/network observations and a commit/build manifest, plus independent test-effect receipts where needed. Keep those evidence layers distinct and bounded.

## Navigation and viewer refinements included

Independent review found that `nextWorkspaceAction` in `app/page.tsx` initially checked the unacknowledged journey before the model report. Root corrected this before release preparation: an unfinished model run routes to inspection/closure ahead of the generic delivery lock, and a non-compatible model report awaiting review takes priority over the journey acknowledgement. Compatible evidence preserves the ordinary journey sequence.

This is navigation selection, not an acceptance or verdict decision. Current report decisions and server-side guards still block acceptance as required; the displayed diagnosis continues to use the actual current file digest. The comparison view also prioritizes an unfinished current run and does not compare older completed reports as evidence of that pending run.

The offline viewer now names the new optional source-mapping/model-explanation checks and separates unknown future check names from actual schema/structure failures. This closes the misleading display warning; it does not broaden offline verification into authenticity or execution proof. Final hosted publication and browser observations remain a separate release check.

## Competitive assessment boundary

The most differentiated current claim is specific: a finite, independently checked concurrent-state model can reveal a controlled native-record loss that the prior sequential journey did not reveal, and the product now presents the resulting evidence more usefully. That claim is narrower and better supported than “AI certifies any outsourced website.”

Completing priority1 improves clarity and actionable depth. External onboarding, a second conflict family, same-version retest storage, independent users/benchmarks and stronger deployment witnesses remain visible gaps. There is no measured award probability, no claim of superiority over every previous winner and no guarantee of winning.
