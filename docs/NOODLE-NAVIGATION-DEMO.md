# 双语面馆交付：从原文到验收时证据

这是一个可重复的静态网站交付练习，使用仓库内的虚构面馆文件。它检查菜单、语言页面之间的导航及到店说明入口，不会创建预约、发邮件、下单或使用真实资金。

先按 [README 的无密钥启动方式](../README.md#run-locally)启动项目；也可在你已获准访问的工作区操作。选择自己的项目，使用默认“双端体验 · 模拟付款”。无需调用 DeepSeek 即可走完本练习。文件来源是 [project.json](../tests/fixtures/noodle-navigation/project.json)、[v1](../tests/fixtures/noodle-navigation/v1/index.html) 和 [v2](../tests/fixtures/noodle-navigation/v2/index.html)。

## 1．创建并核对本次范围

项目名称填写“**双语面馆：菜单与到店说明导航**”，金额填写 **1.00 AUD**。网站需求粘贴以下五句，每句一行：

```text
展示英文菜单和价格。
提供中文菜单页面。
可以从中文菜单打开到店说明。
所有页面在手机可读。
真实预约处理和邮件发送不属于本次交付。
```

进入“验收标准”，逐条查看原文。前四句选择“纳入人工验收”；第五句选择“本次明确不做”，理由填写：

```text
本阶段只交付静态页面和导航；真实预约处理及邮件发送另行约定和验收。
```

这一步必须明确记录排除理由。若选择“待澄清”，或没有填写排除理由，就不能确认创建。每个纳入的原文分组会单独成为人工检查；分组基于标点，不保证自动理解其含义。一个分组里写了多项要求时，买家必须全部检查，也可返回上一步用换行细分。

展开“补充页面与检查方式”，要求页面填写：

```text
index.html
menu-en.html
menu-zh.html
visit.html
```

添加三个浏览步骤：

| 来源页面 | 链接可见文字 | 本地目标 |
| --- | --- | --- |
| `index.html` | `View menu` | `menu-en.html` |
| `menu-en.html` | `中文菜单` | `menu-zh.html` |
| `menu-zh.html` | `查看到店说明` | `visit.html#consultation` |

保留额外人工标准为空即可，因为前四句原文已被纳入。确认原文处理决定后创建，再由买家检查并锁定约定。保存后的“原始需求及本次范围”应能显示完整原文、纳入条目和第五句的排除理由。

## 2．卖家交付有问题的第一版

切到卖家端，选择整个 `tests/fixtures/noodle-navigation/v1` 文件夹。该文件夹含四个 HTML 页面和 `site.css`；不要上传外层目录或把 `project.json` 混入交付。

保存文件并查看规则结果，再运行“浏览器检查”中的链接行为与资源检查。计划应有 **14 项**：四个页面 × 两种宽度，共八项页面资源观察；三个链接 × 两种宽度，共六项链接观察。

第一版中，英文菜单的“中文菜单”链接错误地指向 `index.html`。源码规则应指出第二个约定链接不符合目标；浏览器步骤应将这个错误目标记为未验证，不能把回到首页算作语言切换成功。本轮本地实际保存结果为：规则一项失败；浏览器十二项已观察、零项不匹配、两项未验证。错误目标未被计为符合预期。

卖家提交交付说明，例如“提交菜单与到店说明页面，请核查语言导航”。买家查看第二步对应的证据后提出修改：“英文菜单的中文入口跳回首页，请改为 `menu-zh.html`。”

## 3．提交修订版并保存报告 A

卖家上传整个 `tests/fixtures/noodle-navigation/v2` 文件夹作为替换版本。替换是完整文件集，不与旧版合并。第二版将“中文菜单”正确指向 `menu-zh.html`，其余页面和样式保持练习范围内的静态内容。

卖家保存、运行当前版检查并提交修订说明。买家打开新版，重新运行十四项浏览器观察，将这次实际保存的报告称为 **A**。本轮本地实际保存了十四项已观察、零项需复核、零项未验证；另一次布局检查为八项测量、零横向溢出、零不可用。开发者还在 375px 预览中依次点击首页、英文菜单、中文菜单和到店说明，实际检查了截图可读性。这些结果只覆盖这组静态页面、宽度和链接，不表示预约、邮件或后台已经工作。

买家还需要亲自检查英文菜单与价格、中文菜单、到店说明入口，以及所有页面的手机可读性。完成所有纳入的原文检查和手机检查后，明确接受当前交付版本。检查结果不会代替这个决定。

## 4．验收后再测，仍能回看当时的 A

在“检查历史与验收时证据”中查看新保存的验收快照。它应绑定刚才报告 A 的标识；如果当时没有布局或 AI 报告，应显示“当时没有”，不能用之后的结果代替。

再运行一次同版本的浏览器检查，把新报告称为 **B**。随后刷新，并核对：

- 检查历史里 A、B 都能打开，内容各自保留。
- 验收快照仍引用 A，没有切换为最新的 B。
- 当前交付版本和人工验收决定未被补充检查改写。
- 打开第一版历史仍能看到它自己的文件和故障记录；第二版报告没有被放进第一版。

本练习到此即可结束，不必付款。若继续演示付款，只使用项目明确标注的模拟流程，或已单独配置并获准使用的 PayPal Sandbox 虚拟资金；真实卖家结算与托管不在本项目范围内。

## 记录边界

本轮已通过真实本地 UI 完成四条原文纳入、一条原文排除并保存理由；空理由阻止创建，修改原文使确认失效。五个人工检查确认后，v2 被明确验收，未付款。之后的报告 B 追加为第二份浏览器记录，布局记录仍为一份；导出逐字比较确认验收快照未变，状态仍为已验收、未付款。历史和验收快照在 UI 中均可打开。

这里的 A、B 是讲解名称，不是伪造的报告 ID，请以实际保存的标识和时间为准。本次由开发者操作同一账号的两端，不是陌生用户研究。验收快照保留当时真实 AI 报告；后来的同源模型对比没有覆盖它。具体结果及模型解释限制见[覆盖与证据记录](DELIVERY-COVERAGE-2026-11-02.md)。这些本地结果不证明本轮已经上线、完成连续录屏或完成独立用户试验。
