# 每一轮必须对照冠军：执行规则

用户于 2026-11-04 明确要求：**每一轮循环都必须检测和冠军有什么差距。** 此规则适用于之后每一轮产品改进；一次实现、几次 AI 回复或一次测试不能分别冒充多轮完整循环。

## 一轮的固定顺序

1. **先比较。** 从已确认的总冠军或相关获奖项目中，选至少一个与本轮问题相关的参照。写清比赛、年份、准确奖项、官方来源及核实日期。记录它可观察的强项、我们的起点和证据缺口。
2. **确定主差距。** 每轮优先解决一个明确的主差距，可附带必要的关联修复。把差距转成实际用户任务和可检验门槛，优先关注功能深度、真实交付接入、复杂检验、AI 对任务的实际贡献及结果说服力。
3. **与 DeepSeek讨论。** 提供相关获奖证据、当前实现和本轮门槛，要求它针对同一维度提出方案或反例。只发允许的有限源码与虚构测试材料。主代理独立判断反馈，保留采纳、驳回、待验证的理由；不能把两名 AI 同意当作用户效果证据。
4. **实现和验证。** 实际修改代码；按变更层次验证领域规则、真实路由、数据库持久化、角色、异常、换版与页面操作。记录具体版本、输入、场景、结果和验证限制。
5. **再比较。** 用相同参照、维度和门槛对照修改前后。明确本轮缩小了哪一项差距，什么仍未解决，是否引入新问题。代码审查和功能测试可以支持我们的实现事实，不能自动证明对方实现更弱。
6. **带着剩余问题进入下一轮。** 持续保留差距 ID、未完成原因、下一步可检验动作。未测项目不能从表中消失；被用户暂缓的事项继续标记暂缓，不重新推动录视频或正式提交。

每轮完成时，必须交付模板中的“前后差距表”。只有测试结果、版本号、功能清单或“达到获奖水平”的形容词，均不算完成对照。

## 固定比较维度

| 维度 | 每轮必须回答的问题 |
| --- | --- |
| 用户价值 | 小店主是否能理解输入、结果和下一步？能否完成实际网站外包任务？ |
| 功能深度 | 是否能处理复杂分支、失败、未知、换版、复测和范围变化？ |
| AI 实际贡献 | AI 的判断是否有原文／交付证据支持，并能推动具体行动？错误和弃权如何处置？ |
| 完整产品流程 | 买家要求、卖家交付、检验、返工、复核与独立付款是否衔接且持久保存？ |
| 可信度与说服力 | 结果能否追到准确版本、原始观察和人工决定？外部人能否独立复查？ |
| 易用性与真实接入 | 非开发者能否自行操作？陌生卖家接入是否仍依赖运营方和预设协议？ |

上述是工程对照维度，不是新增的官方评分标准。PayPal 官方评分维度仍以其[正式规则](https://paypalaihackathon.devpost.com/rules)为准；呈现材料在用户当前暂缓范围内，不能因此把所有竞赛差距标为关闭。

以上前三项链接在 2026-11-04 重新读取。后续轮次复用稳定的获奖事实可以引用该核实日期；新增功能、在线可用性、评委偏好等不稳定或未核实声明必须另行查证。网页宣传、作者展示、源码阅读、亲自操作、独立测试分别标明，不能互相替代。

结论使用“本轮门槛已满足／部分缩小／仍未验证／暂缓／出现回退”。这些状态描述我们的证据，不等于判断我们整体超过冠军。没有同条件实测依据时，不给“只差百分之几”、主观总分或获奖概率。
