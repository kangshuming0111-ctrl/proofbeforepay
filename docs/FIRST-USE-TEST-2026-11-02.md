# ProofBeforePay 首次使用测试计划 · 2026-11-02

**状态：真人测试尚未进行。** 本文件是待执行计划和空白记录表；没有参与者、成功率、完成时间或满意度结果。AI 代码评审、自动化测试和开发者走查均不能作为这里的真人测试结果。

目标是观察第一次接触网站的人是否知道下一步在哪里，能否在不上传合同的情况下说明要求，以及能否分清规则证据、AI 建议、浏览器观测、人工验收和付款。先找三位不同的人做小规模发现问题，不用三个人的表现代表所有用户。

## 参与者与材料

计划邀请三位真实参与者：一位不做网站开发的小商家或店主；一位做过网页交付的人；一位没有参与本项目设计的普通网站使用者。角色和语言只是招募目标，记录实际情况时再填写。找不到参与者时保持“待进行”，不要用开发者本人或 AI 补齐人数。

使用专门的虚构测试项目，不输入真实客户合同、电话、邮箱、支付资料或 API key。操作者可在测试设备上使用已有的受控演示账号，不需要让参与者注册付款账号。开始前请参与者同意观察；录屏另行征求同意，不录密码和其他账号页面。

网站版本、浏览器、屏幕尺寸和所用样例必须先记下。外部来源样例位于 `outputs/four-improvements-2026-11-02/licensed-fixtures/`；只上传每包的 `adapted/` 文件，原始下载、许可证和说明是留档材料。样例中的店名、地址、价格等属于原作者虚构演示内容，不是实际商户事实。具体来源与改动以每包说明及清单为准。

## 主持方式

开场可以读：“我们在测试这个网页是否好用，不是在测试你。请边操作边说出你想做什么、觉得会发生什么。卡住时先告诉我你在找什么。我会记录问题；你随时可以停止。”

先给任务目标，不教按钮位置。让参与者独立寻找入口。连续约两分钟没有进展时，先问“你现在想找什么？”，再按需要给提示，并记录次数和原话。主持人代操作的步骤不能计为独立完成。AI 分析是可选的；不用 AI 不算失败，也不要为完成观察而反复触发付费模型调用。所有支付任务只问理解，不进行充值、实际扣款或真实转账。

## 任务卡

| 编号 | 给参与者的目标 | 观察内容 |
|---|---|---|
| T01 | 你在墨尔本开面馆，要外包一个展示菜单、价格和营业时间的网站。没有合同，只描述要求，创建一份你愿意交给承包方的项目约定。金额使用虚构测试金额。 | 是否发现合同可选；能否找到继续按钮；是否知道还要确认标准。 |
| T02 | 现在你是承包方。把主持人给你的完整网站文件夹作为交付，确认页面、样式和本地照片是否保留，并准备让买家查看。 | 能否选择文件夹；是否理解文件夹内的相对路径；是否知道上传后要做什么；照片缺失时如何判断。 |
| T03 | 买家认为一条已约定要求没有达到。请查看依据，准备一条可编辑的修改意见，确定它已经发送或尚未发送。 | 能否从问题定位到证据与草稿；会不会把加入草稿误认作已退回；能否用自己的话区分 AI 建议和规则结果。 |
| T04 | 承包方提交新版后，请找出你上一条意见对应的旧版和新版证据。告诉我你现在能确定什么、还不能确定什么。 | 能否找到逐项版本对照；是否误把新版、问题数量减少或 AI 支持当作修复已确认；不可用记录是否看得懂。 |
| T05 | 如果你认为还要亲自检查手机体验，请完成对应的人工检查流程。停在最终接受交付或付款之前，说明接下来的按钮分别会做什么。 | 是否能找到下一待检查项；是否知道接受交付与付款不同；是否认为系统已经自动替自己决定。 |

建议分工：参与者 1 优先 T01、T03、T05；参与者 2 优先 T02、T03、T04；参与者 3 优先 T01、T04、T05。主持人可预先准备各任务状态，记录准备过程，不能把主持人完成的前置流程计入参与者完成时间。任务因当前网站限制无法执行时，记录“功能不可用”，不记为参与者失败。

每项任务结束只问两句：“刚才你最不确定的是哪里？”“你以为下一步会发生什么？”先记用户原话，再写解释；不要替参与者表达满意或理解。
